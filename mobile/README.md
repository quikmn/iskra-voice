# Iskra for phones (Capacitor)

One app shell for phones: [Capacitor](https://capacitorjs.com) 8.5.2 around the built web client (`client/dist`), which is
bundled into the app rather than loaded from app.iskra.foo. The app opens without the network, reads as a real app for
App Review (guideline 4.2), and updates its web part with each app release.

- **iOS / iPadOS** (`mobile/ios/`): iPhone and iPad, iOS 16+. Bundle id `foo.iskra.app`, team `BWX2M8XSNZ`, name "Iskra".
  Built and uploaded to TestFlight by `.github/workflows/mobile-ios.yml` on GitHub's macOS runners. Nobody needs a Mac.
- **Android** (`mobile/android/`): Android 7+. Package `foo.iskra.app`, signed with the release key on the owner's
  Windows PC by `scripts/build-android.ps1`; the APK is attached to every GitHub release. It replaced the earlier
  Trusted Web Activity (see `../android/README.md`) and updates installed copies in place.
- **Native push** through the [Iskra push relay](../relay/README.md), **voice with the screen locked**, and the phone's
  own **call screen** (CallKit on iOS, a full-screen call notification on Android).

## Build

### iOS

CI does everything (see [docs/ci-cd.md](../docs/ci-cd.md#ios-app) and the playbook's task "build iOS and upload to TestFlight"):

```
gh workflow run mobile-ios.yml                      # build main, upload to TestFlight
gh workflow run mobile-ios.yml -f ref=v2.0.0-alpha.10
gh workflow run mobile-ios.yml -f upload=false      # build, sign and check only; the .ipa is a run artifact
```

Steps: newest released Xcode on `macos-latest` → push decryption check (`swiftc`, RFC 8291 example) → `client`
`npm ci && npm run build` → `mobile` `npm ci && npx cap sync ios` → `xcodebuild archive` → `xcodebuild -exportArchive`
with cloud signing → checks (bundle id, versions, encryption key, Associated Domains, production push, keychain group,
background modes, the extension's id/versions/signature) → a second export with `destination: upload` sends it to App Store Connect.

Signing is automatic with the App Store Connect API key; there are no certificates or profiles in the repo or in
GitHub. The archive is signed ad hoc (`CODE_SIGN_IDENTITY=-`, so CI never creates development certificates), then the
export signs it with Apple's cloud-managed distribution certificate. If Xcode refuses that, run the workflow with
`-f archive_signing=automatic`.

On a Mac, by hand: `cd client && npm run build`, `cd mobile && npm ci && npx cap sync ios && npx cap open ios`.

### Android

On the owner's Windows PC (the release key never leaves it):

```powershell
.\mobile\scripts\build-android.ps1            # mobile\release\Iskra-<version>.apk and .aab (for Google Play)
.\mobile\scripts\build-android.ps1 -ApkOnly   # what release-windows.ps1 runs
```

It builds the client, `cap sync android`, runs the JUnit tests, `assembleRelease` (+ `bundleRelease`), then zipaligns
and signs with `devkeys\iskra-android.keystore` (alias `iskra`, password from `devkeys\iskra-android-keystore.txt`), and
checks that the signing certificate's SHA-256 is the one in `client/public/.well-known/assetlinks.json`, the package
is `foo.iskra.app` and the version code is right. It copies `devkeys\iskra-google-services.json` (Firebase's app
config) in for the build and removes it after; without that file the app builds but gets no push (it warns).
CI (`ci.yml`, job `android`) runs the tests and an unsigned release build on every push.

| Tool | Where |
|---|---|
| JDK 21 (Capacitor 8 needs it) | `devtools\jdk-21`, else `JAVA_HOME`, else `C:\Program Files\Java\jdk-21`; or `ISKRA_ANDROID_JDK` |
| Android SDK | `devtools\android-sdk` (platform 36, build-tools 36.1.0; see `docs/ci-cd.md` "Android"). Gradle (wrapper 8.14.3) downloads itself |
| Release key | `devkeys\iskra-android.keystore` + `iskra-android-keystore.txt`. Same key as the old app: never replace it |

### Versions

- iOS: `CFBundleShortVersionString` = the numeric part of `desktop/package.json`'s version (`2.0.0-alpha.10` → `2.0.0`);
  `CFBundleVersion` = `<code>.<run>.<attempt>`. The extension gets the same numbers.
- Android: `versionName` = the version, `versionCode` = `(major*10000 + minor*100 + patch)*1000` + 100+n (alpha.n),
  200+n (beta.n), 300+n (rc.n) or 900 (final): the same scheme as the old app (last: 2.0.0-alpha.7 = 20000107), so
  every release updates the one before.

## How the web client runs inside the app

The page is served by the app itself, from `capacitor://localhost` (iOS) or `http://localhost` (Android; still a
secure context, and an http page may open `ws://` LAN servers). What depends on the page's origin:

| Thing | In the app |
|---|---|
| Iskra servers (WebSocket, uploads, files) | No origin checks on the server; HTTP endpoints answer `Access-Control-Allow-Origin: *`. Nothing to allow |
| Profile pages (framed) | The server's `frame-ancestors` lists `capacitor://localhost` and `http://localhost:*` (ProfilePages.cs, tested) |
| CSP (`client/src/csp.ts`) | Unchanged: `'self'` is the app's origin; Capacitor's bridge script is injected by the web view |
| LAN servers without HTTPS | Work, like the desktop app. Public hosts need HTTPS (they have it) |
| Invite and message links the app shares | Point at the server's web app or https://app.iskra.foo, never the app's own origin |
| Invite links tapped elsewhere | iOS: Universal Links (`#/join/…`, `#/link/…`). Android: App Links for `https://app.iskra.foo/` (Android can't match the `#` part, so any root link opens the app). Both: `iskra://join/…` |
| Microphone, camera | iOS: Info.plist texts. Android: runtime permissions when a page first asks (Capacitor's web view client) |
| Notifications | Native push through the relay (below); the web push service worker isn't used |
| Screen sharing | Not possible in either web view: the button is hidden (`canShareScreen`) |
| Downloads | Server files open in the browser. Files made in the page go to the share sheet (`@capacitor/filesystem` + `@capacitor/share`) |
| Safe areas, keyboard | `viewport-fit=cover` and `env(safe-area-inset-*)`; the web view resizes above the keyboard. Check edge-to-edge on Android 15+ devices |
| Status bar | Light text on dark themes, dark on light themes (follows `data-scheme`); background `#0B0B14` |
| Tips (Ko-fi, PayPal) | Hidden in the phone apps (App Store and Play payment rules) |
| Backups | Android: off (`allowBackup=false`, no cloud backup or device transfer): the app holds account and push keys |

## Push notifications

How it works (details: [relay/README.md](../relay/README.md), [PROTOCOL.md "Native push"](../protocol/PROTOCOL.md#native-push-phone-apps)):

1. Turning on Settings → Notifications → push asks the phone for permission and gets the push token (APNs, plus a
   PushKit VoIP token on iOS; FCM on Android) and this install's own Web Push keys (a P-256 key pair and auth secret,
   made by the app; iOS keeps them in a keychain group shared with the extension, Android in app-private storage).
2. For each server, the app registers the token with the relay together with that server's VAPID key and gets an
   endpoint `https://push.iskra.foo/v1/push/<handle>`, which it gives the server with `push.subscribe { kind: "native" }`.
3. The server pushes to it exactly as to a browser (encrypted to the app's key, VAPID-signed). The relay checks the
   signature, opens the handle and forwards the ciphertext to Apple or Google.
4. On the phone, the **Notification Service Extension** (iOS) or **IskraMessagingService** (Android) decrypts it and shows
   "Alex in #general: …" with the server's name. A tap opens that channel, DM or group. Pushes about the same
   conversation replace each other.

**Privacy trade-off (decided):** real text on the lock screen, decrypted on the phone, instead of a generic "New message".
The relay, Apple and Google only see a token, the time, the ciphertext size and whether it's a call. The server already
knows what it puts in a push (channel mention excerpts; DMs and groups only "New message from Alex", never content).
If decryption fails (it shouldn't), iOS shows the relay's fallback "Iskra: New notification".

All the server's rules apply unchanged: nothing while the app is in front (focus), do not disturb, notification levels
and mutes, blocks, merging bursts.

## Calls and voice in the background

| | iOS | Android |
|---|---|---|
| In a voice channel, app in the background or screen locked | Background mode `audio`, audio session `playAndRecord`/`voiceChat` | Foreground service with a notification "Iskra · In voice: lounge" and a Leave button; audio focus (music ducks) |
| In a DM or group call | A CallKit call (lock screen, Dynamic Island, system mute and end) | The same foreground service ("Call with Alex") |
| Incoming call while Iskra isn't open | VoIP push → CallKit's incoming call screen (Answer / Decline) | Full-screen call notification (over the lock screen) with Answer / Decline, ringtone, 45 s |
| Answer | Opens Iskra (from the lock screen: unlock or tap the Iskra button in the call screen); the app answers as soon as the call arrives | Opens Iskra and answers as soon as the call arrives |
| Decline | Declines (if the app is running; otherwise the ringing times out for the caller) | The same |

What the web app does: `state/nativeCalls.ts` starts and stops the native side with the voice session, maps
"Leave"/"End" from the system to leaving, CallKit's mute to the mic, and answers/declines the call that matches.
The web view keeps the media (WebRTC); the native side only keeps the app alive and tells the system.

**Check on devices** (simulators can't receive pushes or VoIP pushes):
- iOS: a TestFlight build. Push on, lock the phone, get mentioned from another device: the banner shows the real text
  and the server name; tap opens the channel. Have someone call you with the app closed: CallKit rings; Answer, unlock,
  the call connects. In a voice channel, lock the phone for 2 minutes: you still hear and are heard.
- Android: install the APK over the old app (it must update in place, not install a second app). Same checks; the call
  should show full screen on a locked phone (Android 14+: Settings → Apps → Iskra → "Full screen notifications" may
  need allowing), and the "In voice" notification stays while in voice.

**Known limits:** WKWebView's microphone capture in the background depends on iOS keeping the web view's audio alive;
it works with the audio mode and CallKit in testing elsewhere but verify on each new iOS version. Answering from the
lock screen needs the app to open (the media is in the web view). The App Store doesn't allow CallKit in China
mainland: leave China out of availability, or ship without CallKit there. Android 6 isn't supported any more (Capacitor 8 needs 7).

## Universal Links and App Links

`client/public/.well-known/apple-app-site-association` is served at https://app.iskra.foo/.well-known/apple-app-site-association
(`_headers` gives it `application/json`). It lists `BWX2M8XSNZ.foo.iskra.app` for `#/join/*` and `#/link/*` only.
`client/public/.well-known/assetlinks.json` holds the release key's SHA-256 for `foo.iskra.app` (unchanged from the
old app; add Play's app-signing fingerprint if Google Play ever signs the app). Deploy the web app (deploy.yml `webapp`)
after changing either. Check: `curl -sI https://app.iskra.foo/.well-known/apple-app-site-association` and
`adb shell pm get-app-links foo.iskra.app` (Android: `verified`).

## Owner setup (once, in the browser)

1. **Identifier.** developer.apple.com → Account → Certificates, Identifiers & Profiles → Identifiers → **+** → App IDs →
   App → Continue. Description `Iskra`, Bundle ID **Explicit** `foo.iskra.app`. Under Capabilities tick
   **Associated Domains** and **Push Notifications**. Continue → Register. (If it exists, open it and tick both → Save.)
2. **App record.** appstoreconnect.apple.com → Apps → **+** → New App. Platforms **iOS**; Name **Iskra** (if taken:
   "Iskra Chat"); Primary Language English; Bundle ID `foo.iskra.app`; SKU `iskra-ios`; User Access Full Access → Create.
3. **API key role.** App Store Connect → Users and Access → Integrations → App Store Connect API → Team Keys. Cloud
   signing needs an **Admin** key. If the key behind `APPSTORE_KEY_ID` isn't Admin: **Generate API Key** → name
   `iskra-github-ci`, Access **Admin** → download the .p8 (once), then from the folder with it:
   `base64 -w0 AuthKey_XXXX.p8 | gh secret set APPSTORE_API_KEY_BASE64`, `gh secret set APPSTORE_KEY_ID`,
   `gh secret set APPSTORE_ISSUER_ID`. Revoke the old key after the next good release.
4. **Agreements.** App Store Connect → Business: the Free Apps agreement must be active.
5. **TestFlight group.** App Store Connect → Apps → Iskra → TestFlight → Internal Testing **+** → `Friends & family`,
   tick **Enable automatic distribution** → add testers.
6. Testers install **TestFlight** from the App Store and accept the email invite.
7. **The extension's App ID** (only if a build fails with "No profiles for 'foo.iskra.app.NotificationService'"; Xcode
   normally registers it itself): Identifiers → **+** → App IDs → App → Description `Iskra notifications`, Bundle ID
   Explicit `foo.iskra.app.NotificationService`, no capabilities → Register. Rerun the workflow.
8. **Push credentials** for the relay (APNs key, Firebase): [docs/ci-cd.md "Push relay"](../docs/ci-cd.md#push-relay).

### Export compliance

`ITSAppUsesNonExemptEncryption` is `false` (app and extension), so builds don't stop for the encryption questions.
Iskra uses only standard, published algorithms (libsodium: X25519, Ed25519, XChaCha20-Poly1305, BLAKE2b; Web Push's
P-256 ECDH, HKDF and AES-GCM from CryptoKit; TLS and WebRTC's DTLS-SRTP from WebKit), nothing proprietary, in a
mass-market consumer app; that falls under the exemptions for mass-market encryption in Category 5, Part 2 of the U.S.
EAR (License Exception ENC §740.17(b)(1), classified 5D992.c), which App Store Connect treats as "exempt". Other
end-to-end messaging apps make the same declaration (Signal-iOS and Element X both ship `ITSAppUsesNonExemptEncryption = false`).
**For the owner to confirm (not legal advice):** whether the U.S. annual self-classification report applies, and
**France**: supplying end-to-end encryption in France may need a declaration to ANSSI. If unsure, leave France out of
the App Store availability for the public release (TestFlight isn't a store listing) or file the declaration.

## Known gaps

- **Screen sharing** (ReplayKit broadcast extension / Android MediaProjection) and **picture in picture** for video.
- **Swift package versions.** Capacitor's packages are pinned, but `ion-ios-filesystem` resolves "from 1.1.1" on each
  build; commit `Package.resolved` once a CI run produces one.
- Swedish permission texts on iOS (an `sv.lproj/InfoPlist.strings`); Android's notification channel names are translated.
- Google Play listing: the AAB is built; a Play listing needs the owner (Play App Signing, then add its fingerprint to
  assetlinks.json; Play's foreground-service and full-screen-intent declarations for calls).
